# 自然语言需求理解：研究与诊断

日期：2026-10-22。产品保持 C#/.NET 原生栈。当前界面中的 `rules-1.0` 是有限规则基线，不是通用语义模型。

## 查阅的论文与开源实现

## 已执行的广度诊断

`tests/nlp-cases.json` 含 36 条人工编写的诊断输入，覆盖常见任务、CAD、音频、直播、数据分析、并发、容量增长、预算、便携、噪声、功耗、兼容性、时间变化、条件、指代、口语、中英混合、冲突、多用户和文本中的恶意指令。

执行 `PerfCompass.exe --nlp-evaluate`，输出 `artifacts/nlp-evaluation.json` 和 `.txt`。当前规则基线只有 12/36 条的诊断字段集合完全一致，其余缺失和额外字段全部列出。该结果不是抽样真实用户准确率，也不是任何模型的成绩。用例和预期由开发者人工编写，需继续审校和扩充独立输入。

这说明继续扩充少量关键词不能满足通用需求理解。不能为了让数字好看而删除陌生任务、条件、数值与时间用例，或只把规则已支持的字段当成正确答案。

## 下一步的实现与评价约束

采用开放任务名称、固定语义关系的结构：任务/软件、规模、资源或体验目标、预算与其他约束、肯定/否定/条件/不确定、过去/当前/未来、频率、原文证据和待澄清问题。陌生任务保留其原名，不强行归入既有五个场景。

模型只负责提取候选事实，不直接输出购买型号。C# 验证证据能否逐字定位、数值和单位、时间与条件关系、冲突及来源版本。用户核对后，才能成为配置建议的约束；低置信或缺失信息应提问或保留未知。

需要分别测量：结构合法性、原文定位、字段完整性、否定/条件/时间正确性、数字和单位、错误的硬件需求推断、澄清质量、延迟和内存占用。条件与时间表达不能压扁成一个“未来/非未来”布尔值。

本地研究候选为 [Qwen3-4B-GGUF 官方模型](https://huggingface.co/Qwen/Qwen3-4B-GGUF) 配合独立 llama.cpp 进程；下载物放在被 Git 排除的 `.tools/nlp/`，不加入默认安装包。选择只是实验起点，尚无可用于产品部署的通过结论；也没有自动向云端发送用户记录。

## 第一轮本地模型实验

已实测 Qwen3-4B Q4_K_M，原生 llama.cpp b11815，CPU 4 线程，不使用 Python 产品运行时。模型 SHA256 为 `7485fe6f11af29433bc51cab58009521f205840f5b4ae3a32fa7f92e8534fdf5`；运行器官方资产摘要为 `fcdde7412f5a4c6e644008893cba38587c4d1f3800074aa6a72614b8d6a92028`。

第一轮实测 4 条（用例 11/18/23/24），请求约 6.0–24.5 秒。4 条均产生可解析 JSON，输出的 9 项事实引用均可定位到原文，但人工检查发现明显问题：预算用例没有抽出任何事实，重复追问原文已回答的预算范围；时间用例把“现在已经不玩了”标成未来；条件用例混淆肯定与条件，并有引用不能充分支持相应事实的问题。因此不能将 4/4 JSON 合法或 9/9 可定位当作正确理解。

实验还发现了 Windows PowerShell 5 将带文件元数据的字符串深度序列化成巨大请求的问题。已停止该轮自建进程，改用 `File.ReadAllText` 读取提示词，并增加请求长度上限；这是实验客户端问题，不应误判为模型推理耗时。

llama.cpp 官方文档明确说明 JSON schema 只约束生成，并不自动进入提示词。因此下一轮将字段定义同时提供给模型，明确不同事实类别，并用额外的 12 条输入扩展测试。原始第一轮结果保留在本地 `artifacts/nlp-model-baseline/`；改进轮写入不同目录，记录提示词哈希。它们尚未构成独立、足量的准确率评估，也没有接入默认购机推断。

复现实验脚本为 `scripts/evaluate-local-nlp.ps1`，只读取人工诊断用例，使用回环地址服务，结束时停止其自建进程。模型与运行器需独立准备，不能因为脚本存在就认为任何用户机器已具备本地语义能力。

## 第二轮结果与取舍

扩大后的 16 条均完成，均返回可解析 JSON，输出的 19 项事实引用均可在原文找到；请求耗时约 6.7–25.7 秒，后续请求复用了提示词缓存，不能作为所有任务的冷启动性能。

逐条检查已确认如下反例：数据分析用例遗漏明确的 64 GB 下限；便携用例将电脑重量要求的对象写成“背包”，并漏掉六小时续航；预算用例仍漏掉外设不含在预算内的条件；时间用例将过去玩游戏错误地标为排除；条件用例漏掉否则分支；多用户用例将周末习惯标成未来需求。自动检测到“原文存在”并没有阻止这些错误。

因此本轮不将该 4B 模型作为默认语义解析器，也不让这些候选事实自动驱动购机建议。此结论只针对当前模型、量化、提示和样本，不能据此否定其他模型或完整信息抽取方案。下一轮需比较专用抽取模型或更强语义模型，同时保留未知、澄清和用户确认链路；不能靠继续修改当前几条输入的预期来达标。

实验中研究服务的瞬时工作集约 5.2 GiB（8192 上下文，CPU 四线程）。性能监测程序若默认常驻这种本地服务，本身就会改变被测负载；后续部署须按需运行并隔离自身推理开销，或提供经用户选择的其他推理方式。当前研究服务已在批次完成后停止，没有作为后台产品服务安装。

完整人工诊断与模型输出（均为合成输入，不含用户历史）：[规则诊断](experiments/rules-1.0-diagnostic.json)、[第一轮原始输出](experiments/qwen3-4b-baseline.json)、[第二轮原始输出](experiments/qwen3-4b-schema-aware.json)。对应提示词也保留在同目录。这些是可审阅的实验记录，尚非独立基准成绩。

## 已核对事实的数量编译

0.8 增加模型之外的数量编译层：保留事实对象与触发条件，将已核对的范围、严格边界和单位转换成候选比较条件。这借鉴了 [Reading between the Lines（RANLP 2023）](https://aclanthology.org/2023.ranlp-1.76/) 将需求拆成作用对象、条件和要求的区分方式；论文没有验证本项目的数量语法或购机建议。

数量层对照引用中的数字、单位和方向，避免规范化过程把低于改成不超过、把 GB 和 GiB 混用，或把组件预算当成整机报价。40 条人工编写的数量语法用例与原生流程验证见 `QUANTITY_GOALS.md`；这些是数量转换检查，不是模型语义准确率。当前规则解析的 12/36 结果及 4B 模型失败记录依然保留。

8B Q4_K_M 的首次下载曾中断，后续已完成文件校验与 36 条原文的产品调用。原始输出和开发审阅详见 [语义审阅协议](SEMANTIC_EVALUATION.md#8b-基线与逐例开发代理审阅) 及 [逐例报告](semantic-review-8b.html)：7 例完整、11 例有重要遗漏、18 例有语义错误。2026-10-24 又完成独立保存的 24 条扩展输入与逐例开发审阅：4 完整、1 遗漏、19 错误，[扩展报告](semantic-review-8b-extended.html) 保留全部原始候选。这两批都是开发代理对合成诊断集的审阅，不是独立人工标注或通用准确率；没有用接口/引用通过代替语义通过。模型保留为主动启用的可选功能，不进入发布包，也未设为默认解析器。

`PerfCompass.ModelProbe --batch` 直接调用产品中的提取器，读取原有合成用例，逐例记录未确认结果、原文验证问题和量化候选；仅允许回环地址并要求空输出目录。它避免研究脚本与产品在发送文本方式上的差异，仍须人工检查遗漏、主体、否定、时间与条件。只有编译了工具不能证明任何模型已经完成该批测试。

## 4B 模型的产品原始文本全量检查

按产品实际请求方式完成全部 36 条输入，保留 64 项未确认事实，并完成逐例开发代理审阅：3 例未发现遗漏或错误、10 例有重要遗漏、23 例有语义错误。问题包括准备任务标成现在、把并发/测试环境放入触发条件、将预算上限或家人周末游戏错误标成排除，以及费用范围、频率和跨句指代遗漏。原文可定位和 JSON 合法仍未解决这些问题。

这份开发诊断不能作为通用准确率，也没有独立人工标注。本轮仍不将该 4B 组合选作默认解析器。运行清单、输入/输出哈希、分类依据与报告见 [语义审阅协议](SEMANTIC_EVALUATION.md) 和 [逐例报告](semantic-review-4b.html)。0.8.1 的数量转换修复来自其中两条反例，不据此声称模型理解已被修正。
