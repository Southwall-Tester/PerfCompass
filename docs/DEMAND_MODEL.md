# 需求变化与冗余分析方法 1.13

此方法为可解释的启发式规则，尚未通过跨机器、长期用户轨迹校准。资源占用变化不是购买意图或体验改善的直接证明。

## 观测事实与配置推断

0.8.14 起，分析同时保留两类结果。观测事实回答“已测任务中负载偏低、已有实际负载，还是出现过繁忙”，附上观测范围、有效读数时长和覆盖率；配置推断回答“是否已有依据讨论余量、降档或压力”，继续使用下文的任务覆盖、近期证据及历史完整性门槛。因此，尚不能判断整机配置时，界面仍可显示已测任务的初步余量或繁忙线索。

轻负载初判要求相关部件至少有 5 分钟有效读数。CPU 与最忙逻辑核心、内存与提交量分别要求至少 95% 的有效使用时段覆盖，GPU 核心/3D要求至少 90%，并保持同一采集口径。这里的 5 分钟按实际取得的部件读数累计，运行程序或有效使用满 5 分钟但读数缺失仍可能不足；它是早期反馈的启发式门槛，不是典型任务已经覆盖。

| 观测对象 | 轻负载初判条件 |
| --- | --- |
| CPU 与逻辑核心 | CPU P95 <25%，最忙逻辑核心峰值 <70% |
| 内存与提交量 | 物理使用峰值不超过当时容量的 70%，提交量峰值不超过对应物理容量的 90% |
| 已测 GPU 核心/3D | P95 <30%，且未发现需要保留的核心或分引擎重负载；不代表其他引擎闲置 |

繁忙线索先显示，不等待 5 分钟或多天积累：有效 CPU 或逻辑核心读数达到 80%、内存峰值达到当时容量的 90%、GPU 核心/3D或已暴露引擎峰值达到 80%，以及已保存的相应高负载时长，都可提供线索。短峰和部分引擎中的已知重载会保留，但不会因此标为持续压力；持续压力仍使用下文独立门槛。满足观测时长而处于轻载与繁忙条件之间的读数显示为“已有实际负载”。

CPU、内存和核心/3D初步观测使用最近 7 天、当前所选场景的记录；分引擎重任务线索使用当前所选时间窗口，并明确标注“所选 N 天”，不会把较早的重任务改称最近一周。没有前期记录也可描述这些已测事实，周/月需求变化仍必须有可比的前后两期。硬件未隔离、时段重叠时不形成初步观测；其他历史异常会撤下轻负载初判，单独有效的繁忙线索仍可保留。GPU 来源混合时撤下相应的 GPU 轻负载初判，CPU 与内存独立判断。

已确认且相关的新任务、资源/体验目标，以及最近 7 天尚未处理的体验问题，优先于轻负载建议显示；观测依据继续保留。用户可从分析卡片进入“比较候选配置”，逐项核对目标和任务表现。初步余量、疑似过剩或可比较降档、候选任务达标是不同层次，勾选覆盖范围不能代替候选实测，详见 [候选配置比较](CANDIDATE_COMPARISON.md)。方法 1.13 的候选范围校验绑定观测分类和范围；分类或来源范围变化需重新核对，普通数值、时长与覆盖比例刷新不会单独撤销确认。

## 两种权重

统计权重按实际有效采样秒数计算，避免采样密度改变 P95。需求优先级通过独立的时间窗口判断，不把多年闲置与近期新增任务简单平均，也不任意设置一个固定的“近期 70%”系数。

比较最近 7 天与此前 7 天，以及最近 30 天与此前 30 天。两个时期均需达到观测门槛：周比较为每期至少 0.5 小时且跨 2 天，月比较为每期至少 3 小时且跨 3 天；相关传感器有效覆盖均需至少 90%。按所选场景隔离比较；没有记录不等于闲置。

## 增加与减少

- CPU/GPU：近期 P95 至少 60%，并增加至少 25 个百分点；或者负载至少 80% 的时间占比达到 10%、增加至少 8 个百分点且累计至少 10 分钟。
- 内存：绝对使用量 P95 增加至少 2 GiB 或此前值的 25%，取较大者。
- 减少使用对称条件识别，但不据此自动删除过去任务的配置需求。

周与月均增加时优先解释周变化。增加信号约束原来的过剩、适配或待核对结论，要求核对新任务、设置变化和异常后台占用，并确认未来是否持续使用。仅使用时长增加、负载强度不变，不算需求增加。

近期持续压力独立检查最近 7 天：至少 30 分钟且覆盖率至少 90%；CPU 至少 90% 或 GPU 至少 95% 占有效观测 10%，内存使用至少 90% 占 5%。这些是压力线索，仍需结合任务耗时或卡顿判断。

## 冗余保护

基础观察至少 10 小时、跨 3 天，并由用户确认常用任务已覆盖；还要求最近 7 天至少 30 分钟、跨 2 天的有效观测及相应指标近期证据。单核、内存峰值、提交量和显卡峰值保留独立约束。少量重任务不能因总体占比低就被忽略。

0.8.3 起，典型任务确认绑定当前硬件配置。设置保留确认时的配置标识，分析只在当前标识匹配时使用该确认。旧版仅有全局勾选的设置不自动绑定，进入新版本后需重新勾选并保存；升级 CPU/GPU、改变内存总量或逻辑处理器数导致标识变化时也需要重新确认。历史记录不因此删除，达到观测门槛后可重新评估。

程序按当前配置隔离历史，分析入口也会过滤显式选择的配置；未选择且混入多个配置、或记录缺少配置标识时，不生成余量或需求变化结论。确认状态及原因同时写入界面和 HTML 报告。缺少典型任务确认不抹去同一配置已观测到的持续压力线索。候选比较的覆盖确认随硬件配置或典型任务确认状态变化而失效。

配置标识来自 CPU/GPU 名称、物理内存总量和逻辑处理器数，不是物理电脑的唯一身份，也不验证任务是否真的完成。同样配置的另一台电脑可能具有相同标识；复制数据后仍需核对自己的任务覆盖情况。该确认也不能代替近期趋势、传感器覆盖及偶发重任务检查。

默认保留 90 天便于月对照；选择较短保留期可能缺少此前基线。展示的分析时间范围与比较上下文分开，选择最近 7 天不会使此前对照被当作当前使用量。

## 采样边界

### 显卡引擎范围

0.8.13 使用锁定上游提交的 LibreHardwareMonitor 源码修订版，出处及修改清单见 [PATCHES.md](../vendor/LibreHardwareMonitor/PATCHES.md)。驱动查询失败后清除本轮动态值，差分计数失败或中断后重新建立基线；D3D 节点使用独立经过时间，负累计值、回退、非正间隔、超过15秒及超过100%的差分结果保留未知。稳定数值配合推进的有效时间仍是有效读数，不能因为数值不变就认定缓存。原生 API 成功也不能证明驱动内部数据新鲜或物理准确。

新记录使用 `gpu-engines-1.1`，增加 Intel 的“渲染/计算（合并）”与“媒体引擎（合并）”标签，不拆成推测的纯计算或纯编码。`GpuMetricSource` 记录旧核心/3D字段实际来自 `GPU Core`、`GPU D3D 3D` 或 `D3D 3D`；旧记录未保存来源时显示未标注。来源或采集协议改变时不合批，前后时期不同口径不生成需求增减。所选窗口混合口径不生成核心/3D降档核对结论；近期同口径的有效重载仍可保留压力线索。候选比较范围绑定这些来源；CSV 和 HTML 同时显示出处。

0.8.13 的展示也遵守来源边界：所选窗口的有效核心/3D观测混合来源或规则时，撤下合并 P95；历史图只要混入不同口径的实际 GPU 观测，就撤下该范围的 GPU 曲线，CPU、内存曲线独立保留。场景 P95 按各场景自身来源检查；切到同口径场景后可以显示该场景的 GPU 统计与曲线，不受其他场景混合来源影响。实时图在核心/3D来源或规则切换处只断开 GPU 连线，保留切换后的实际点和其他曲线。原始记录及 CSV 可读行中的来源与数值保留。

周/月对照若在同一个时期内部混合来源，则不显示该期合并 P95，负载比例也暂不解释；前后两期各自同口径、只是彼此来源不同，可以分别显示各期读数，但仍标明不可据此判断需求变化。混合口径下保留已观察峰值与重任务提示，不凭缺失的 P95 将其称为“偶发”；部分引擎重载也不能把因证据不足而未知的配置判断提升为适配。近期同来源且满足时长、覆盖和负载门槛的压力线索，不因更早时期的来源不同被抹去。

活动规则升至 `activity-1.3`，阈值不变，升级后的有效 GPU 证据来源改变，所以旧代表性确认需重新核对。旧1.0引擎记录与1.1/1.2活动记录仍可读取，原始文件不改写，也不能追溯修复旧缓存。节点的运行时基线绑定 LUID、节点编号和名称；历史仍只保存名称及数量，不能证明跨驱动版本的节点身份或统计可比性。

0.8.12 保留旧 `Gpu/GpuPeak/GpuCoverage` 的核心/3D口径，新增 `GpuEngineVersion=gpu-engines-1.0` 与 `GpuEngines`。仅分类已知执行引擎标签：核心、3D、计算、合并视频、编码、解码、视频处理、复制；同类取已知节点的最大值，保留名称与重名节点。内存控制器、总线、功率比例及未知名称不猜成执行引擎。缺失类别保留未知，不能推断硬件不支持；不同引擎不可相加。[Microsoft 的引擎统计说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)解释了仅看3D或平均各引擎可能漏掉工作。

约10秒批次保存各类别的时间加权平均、峰值、已观察秒数、类别完整秒数及≥80%/95%秒数。来源集合或同名节点数量在批次内改变时保留观测和峰值，但该批次不提供完整类别时长。新活动规则 `activity-1.2` 将任一已知执行引擎≥20%纳入活动线索；旧 `activity-1.1` 历史仍可读取，典型任务确认需要重新核对，旧版漏记时长不补造。

0.8.13 修正 GPU 分引擎合批的浮点端点问题：一个类别只有一项有正观察时长的有效读数时，直接保留该项负载，避免“乘时长再除时长”引入舍入误差；多项有效读数按已观察秒数加权后，将计算所得均值限制在这些输入负载的最小值与最大值之间。该处理利用有效加权平均应处于输入区间内的性质，避免舍入使均值略高于独立保存的峰值。峰值仍取实际输入峰值，不随均值抬高；无效输入不因端点处理变为有效。

旧文件若已经保存“负载高于峰值”等矛盾，即使差异只有一个浮点步长，仍按历史异常诊断并保留原件，不自动改写成修正后的结果。实际 `HistoryAnalysis` 入口报告文件与行号，保留其余可用观测，并按历史异常保护暂停余量和时期变化结论。新合批修复不能追溯证明旧观测正确。

分引擎历史 P95 按同一规则和来源范围内的合并记录与已观察时长计算；所选窗口的类别存在多个来源范围时，P95 不混算，已观察峰值与重载时长仅作为任务线索保留并说明。来源范围包含采集规则版本、传感器名称及重名数量；部分读数可能低估同类最大负载。类别完整只表示当时已暴露的同类节点读数有效，不能当作整张 GPU 覆盖。周/月对照与近期持续压力只使用完整读数，完整与部分读数混合后的均值不能拆回完整均值，所以整批不参与该对照。前后时期来源集合变化时也不推断需求增减。已知重负载、偶发峰值与近期增加分别约束核心低负载提示；均不直接证明瓶颈或升级收益。老历史缺少新增字段，不能将它补成此前引擎闲置。

当前仍只分析界面标明的第一张 GPU，不合并不同显卡。0.8.12 所复用的上游 [LibreHardwareMonitor 0.9.6 节点采样](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/3d331e3370efb858411f19511373eff65a218701/LibreHardwareMonitorLib/Hardware/Gpu/NvidiaGpu.cs)可能在内部查询失败但外层更新正常返回时保留旧值，其 [D3D 查询](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/3d331e3370efb858411f19511373eff65a218701/LibreHardwareMonitorLib/Hardware/D3DDisplayDevice.cs)使用日历计时。0.8.13 的源码修订针对已识别的失败路径、差分基线和设备对应关系增加保护，详见本节开头及修改清单；这些保护和上述合批数值修复均不能证明驱动成功返回的数据新鲜、物理准确，也未证明跨驱动和多 GPU 适用性。

### CPU与活动线索

0.8.11 起，Windows CPU 计时记录必须覆盖本次全系统活动逻辑处理器数，并核对读取前后的处理器数和分组数。缓冲区长度必须完整、前后记录数量及分组一致，每个处理器的空闲/内核/用户计时必须非负、单调，内核与用户增量之和必须为正，空闲增量不得超过总增量。任一项不满足时，本次整机 CPU 和最忙单核均未知；不跳过无增量处理器后再将剩余部分称为整机，也不把异常裁剪成 0% / 100%。先减累计值、再以浮点数求和，避免累计 Int64 相加溢出。完整整机负载按各处理器忙碌时间之和 / 总时间之和计算，最忙单核按各自比例计算。

缺失 CPU 不增加合并记录的 CPU/单核覆盖时长；其他实际取得的内存、GPU 等读数继续独立使用。实时页说明 CPU 计时待恢复，后续完整计时重建基线后恢复。旧记录没有原始处理器计时，不能追溯验证或重算；原始历史继续保留。分组计数一致也不证明运行中硬件拓扑与处理器对应关系始终不变，尚无物理热插拔或跨分组硬件实测。Windows 原生接口的未来兼容性与驱动故障仍需单独验证。

0.8.10 / activity-1.1 将近期有效键鼠输入、整机 CPU ≥20%、单个逻辑处理器 ≥80%、GPU ≥20%、磁盘繁忙程度 ≥80% 或已观测读写吞吐合计 ≥20 MiB/s 作为活动线索。单个有效吞吐读数达到门槛也可提供线索，另一个缺失值仍保留缺失。整机平均负载低不能排除单核或慢随机 I/O 任务；后台维护同样可能被计入，活动标记不证明任务属于用户需求，更不直接证明瓶颈。

每条新记录保存 `ObservationVersion`，CSV 增加 `observation_version`。旧记录未标版本时按旧字段读取；未知的非空版本不参与配置推断，并进入历史异常诊断。典型任务确认增加 `RepresentativeObservationVersion`，绑定当前硬件与活动规则。旧版确认保留但不自动升级，需在当前版本重新运行相关任务并勾选保存；修改后旧候选比较范围需重新核对。旧合并记录可能已经把无人值守任务保存为 0 秒，无法据已有字段补回有效时长，原件继续保留。

活动判别仍是启发式：传感器缺失、间隔内短任务或未超过门槛的工作可能无法识别，不能从未计入的时间证明没有重要任务。余量门槛、峰值、近期趋势、覆盖率与候选实测仍共同约束购机建议。

约 2 秒原始采样合并为约 10 秒记录。新记录保留 GPU 峰值及 CPU ≥90%、GPU ≥80%/95%、内存 ≥90% 的采样持续时间；CPU ≥80% 的趋势时间仍按合并后的平均负载估算。旧记录缺少新增字段时使用平均值估算，无法补回未保存的短峰。P95 基于合并记录，采样间隔内的瞬时波动仍可能遗漏。

0.8.5 起，硬件传感器先更新设备及其所有子设备，再复制本次读数。任何更新或读取抛错时，该设备本次的负载、显存和温度留空，不沿用缓存，也不临时改为另一张显卡。其他设备继续，Windows CPU 与内存基础采集独立进行。实时页显示失败设备并在下次采样自动重试；成功后清除提示。负载越界或非有限值、负显存值也不当作有效读数。

合并历史中仍保留已观测的有效使用时间，但失败指标不增加相应传感器覆盖时长，不以零负载填补。例如 10 秒有效使用中 GPU 仅 8 秒有值，覆盖率为 80%，不是 10 秒低负载。新采集逻辑无法修复旧版可能已保存的缓存值；更新 API 成功也不证明驱动内部一定提供了新值。本轮验证使用受控抛错，不是物理驱动故障或休眠恢复实测。

目前只选择一个 GPU 进行分析，多 GPU 并行任务尚需扩展。尚不能从占用率直接推导某款 CPU/GPU 的购买型号或节省金额。

## 历史完整性

### 计时与中断

0.8.8 起，采样同时读取日历时间和独立的经过时间计数器。日历时间用于定位记录；正常时有效时长取 UTC 跨度与计数器跨度的较小值，避免小幅校时增加使用时长，也避免相邻历史时间片相互侵占。两者差值超过 0.25 秒、日历跨度不为正、经过时间不可用，或任一采样跨度超过 15 秒时，该段有效时长为零，重建基线后继续采集。0.25 秒是容差，不是已校准的硬件精度或校时保证；短于容差的变化不会被明确分类为中断。

中断记录单独保存，`SamplingIssue` 为 `clock-change`、`poll-gap` 或 `invalid-elapsed`。这些代码描述时间校验结果，不直接证明用户调过时钟或电脑进入过睡眠；调度延迟也可能影响读取。中断记录不能携带正的有效秒数，未知状态或矛盾记录按历史异常处理；所有检查通过后才交给分析器。零时长段不参与压力、余量或负载曲线，不将缺采推断为空闲。实时页重建体验记录和曲线上下文，历史页及 HTML 显示中断数量，CSV 增加 `sampling_issue` 列；老记录缺少此字段时按原格式读取，不追溯补造中断原因。

自动分析、历史清理与进程列表的刷新间隔使用独立经过时间调度；进程 CPU 比例也以经过时间计算。暂停会重置采样、CPU 和进程基线，恢复后不累计暂停区间。参考 [.NET Stopwatch](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.stopwatch?view=net-10.0) 的经过时间机制。时间源替身和本实例输入注入不修改系统时钟，不代替真实睡眠、休眠、Windows 校时、长期计数器稳定性或跨设备验证。

系统日历长期设置错误仍会影响绝对日期和周/月归属；本逻辑不从网络校准系统时间。缺少有效时段和存在历史重叠时，仍分别遵守观测门槛与历史异常保护。方法升级至 1.8 后，候选比较范围需要重新核对。

### 格式与读取

0.8.6 起，实际分析入口检查当前窗口与时期对照所用历史，读取范围为两者所需天数的较大值（至少 60 天）。检查 JSON、UTF-8、重复字段、时间、硬件标识、有效状态及 0–15 秒采样时长；空行、BOM、未知扩展字段及完整但没有末尾换行的 JSON 可读取。时间及归属明确的其他硬件记录、范围外日期不纳入本次异常；无法确定时间或归属的损坏行按可能相关处理。

发现异常时保留可解析的观测、时长与已观测压力线索，基础统计不等于完整证据。暂停配置余量、待验证降档和时期变化结论；界面及 HTML 报告列出文件与行号，最多展开 50 处，并显示全部计数。未发现格式异常也不能证明未采集时段、被删除文件或任务覆盖完整。原文件不因分析被改写，可通过数据保护备份、从已核对备份恢复到新目录。

读取时在本实例追加锁内固定文件长度，只扫描该前缀，随后追加内容留给下一次分析。单行超过 4 MiB 时流式跳过并记录异常，不将后续完整记录一并丢弃。另一程序直接修改或截短文件不受本实例锁保护，读取错误会明确显示；这不是对恶意并发修改的隔离保证。

异常位置、类型与损坏内容校验参与候选比较上下文；新异常使旧覆盖确认失效，异常消失后也不自动重新勾选。用户可继续逐项核对有独立依据的候选条件，但比较仅覆盖这些条件，不覆盖无法读取的历史任务。方法升级至 1.6 后，旧比较范围也需要重新核对。

原始采集较慢时，合并器在下一次读数将使批次超过 15 秒前保存已有批次；避免生成随后被分析器排除的超长记录。这不补回旧版已丢弃、未写成功或未采集的时段。

### 重复与重叠时段

0.8.7 / 方法 1.7 起，实际历史分析入口 `HistoryAnalysis` 对有效记录去除行首尾空白后计算 SHA256，相同字节的副本只使用一次，界面与 HTML 显示排除数量和位置。没有其他异常且原有证据充分时，重复副本不撤销余量资格或候选覆盖确认。原始文件不改写，CSV 仍保留原始可读行；备份仍保存原字节。JSON 字段顺序或内部空白不同的记录不当作完全相同的副本。

不同记录的有效时段采用 `(时间 - 有效秒数, 时间]`，按 UTC 时间片并集计算同一配置的唯一有效时长。每个场景也按自身时间片并集计时；同一时段可能有多个场景标签，场景时长不能相加。非相同记录发生重叠时，负载份额和来源无法确定，所有历史部件建议保留未知，撤下 P95、峰值、重负载比例及历史曲线，暂停时期对照与余量结论，并要求重新核对候选覆盖范围。保留的唯一时长不能证明期间连续采集或任务已完成。

配置标识不是物理设备唯一身份，程序不能从重叠记录确定哪一条属于哪台同配置电脑，也不自动选择可信来源。去重保留每条有效记录的固定长度摘要及压缩后的时间区间，摘要内存仍随记录数增长。直接调用底层 `AnalysisEngine` 的内存数据不经过文件去重；生产界面与 HTML 生成流程使用已审计的实际入口。方法 1.7 升级后，旧候选范围需重新核对。

## 体验与用户确认需求

最近 7 天尚未处理的体验记录会暂停过剩或待验证降档建议，不会将相关资源自动判为瓶颈。记录可在历史页标为已处理；这表示用户已核对问题，不是程序证明问题已经解决。

设置中的有限规则预解析只处理部分任务、否定和未来线索。用户确认保存的本地 AI、新增重任务或显示目标会约束相应的降档候选；云端 AI 不自动增加本地 GPU 和内存要求。改变原文后，旧确认失效。原文中的未知条件、数字和任务仍可能未被正确解析，不能把规则基线当作完整需求理解；详情见 `NLP_RESEARCH.md`。

可选模型接口增加逐项核对后的开放需求。明确的未来任务和资源/体验目标会约束余量结论；资源事项按可辨认的部件关联，预算与便携不自动变成更高算力。条件、不确定和过去需求保持独立，不能作为必然的未来任务。带实际触发条件的事项不能被保存为无条件要求。仍需在候选机器上验证，尚未实现完整数值约束、性能与价格联合求解。
